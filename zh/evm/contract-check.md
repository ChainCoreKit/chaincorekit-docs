# 合约检查（Contract Inspector）· EVM

> 输入地址，看它有没有代码、是不是代理、实现在哪、是否被 EIP-7702 委托。只读，不连钱包。

## 什么时候用

- 拿到一个合约地址，想先弄清它是不是代理、真正的逻辑在哪个地址。
- 要在 ABI 调用工具里操作某个合约，但不确定该用代理地址还是实现地址的 ABI。
- 看到一个「有代码的地址」，想确认它是传统合约还是被 EIP-7702 委托的普通账户。

## 使用步骤

1. 选**网络**，填**合约地址**。
2. 点**开始检查**。工具会读取运行时字节码，并依次探测四种代理槽与 EIP-7702 委托标记。

## 输出说明

| 项 | 含义 |
| --- | --- |
| 运行时字节码大小 | 为 0 即该地址没有代码 |
| 代理模式 | 命中的模式及其目标地址、所在槽位 |
| EIP-1967 admin 槽 | **代理的管理员**，负责升级实现 |
| EIP-7702 委托 | 命中时说明该地址是 EOA 而非传统合约 |

探测覆盖：EIP-1967（实现 / 信标 / 管理员）、EIP-1822（UUPS）、OpenZeppelin 旧版槽，以及 EIP-7702 委托标记。

## ERC-165 接口探测

检查完成后，页面会顺带探测这个合约支持哪些标准接口（ERC-721、ERC-1155、ERC-2981 等）。

判定按 **EIP-165 自己规定的两步流程**做：`supportsInterface(0x01ffc9a7)` 必须返回 true，**并且** `supportsInterface(0xffffffff)` 必须返回 false。第二步不能省——一个对任何输入都返回 true 的合约，只做第一步会被判成「支持全部接口」，之后逐个探出来的结果全是假的。这种合约本工具会直接标为「未实现 ERC-165」。

三种结论含义不同：

| 结论 | 含义 |
| --- | --- |
| 实现了 ERC-165 | 通过了上述两步判定，下面列出的接口可信 |
| 未实现 ERC-165 | 已确认不合规。**这不说明合约有问题**，只是它没有这种自述接口的方式 |
| 无法探测 | 调用失败或返回了非标准值。**不代表它不支持任何接口**，只代表这条路探不出来 |

收录的接口有限，「实现了 ERC-165 但没命中」也是正常结果。

## Interface ID 计算

页面下方是一个纯本地的计算器：填入函数签名（每行一个），算出对应的 interface ID。不需要地址，也不需要 RPC。

两条容易记错的规则：

- **是所有函数选择器的异或**，不是拼接后哈希。记错之后算出来的仍是一个格式正确的 `bytes4`，拿去 `supportsInterface` 查只会得到 `false`，看不出是自己算错了。
- **只算函数，不算事件；继承来的函数不自动包含。** `ERC721Metadata` 的 ID 只由它自己新增的 `name()` / `symbol()` / `tokenURI(uint256)` 三个函数算出，不含 `ERC721` 的那九个。

某一行签名写错时会指出**具体行号**。结果是 `0x00000000` 时会提示检查重复签名——异或的性质会让重复项互相抵消。

## 注意事项 & 常见坑

- **「未检测到已知代理模式」不等于「不是代理」。** 这是本页最重要的一条。合约完全可以把实现地址放在自定义槽里——**USDC 就是这样：它是代理，但 EIP-1967 三个槽读出来全是 0**（FiatTokenProxy 用的是自己的槽）。所以工具只会告诉你"没检测到"，永远不会说"这不是代理"或"不可升级"。
- **admin 槽不等于 owner。** admin 是代理的管理员、负责升级实现；业务合约的 `owner()` 是另一回事，两者可以是完全不同的地址。看到 admin 就断定"这个地址控制一切"是错的。
- **有代码不再等同于合约账户。** 在支持 EIP-7702 的链上，普通账户也可以带一段 `0xef0100 ‖ address` 的委托代码。工具会单独识别并说明。
- **只探测已知模式。** 只查 EIP-1967 会漏掉 UUPS 与 OZ 旧版，而漏掉之后给出的"未检测到"更容易被误读，所以这里四种都查。
- **不获取源码与 ABI。** 那需要区块浏览器的 API，不在本工具范围内。
