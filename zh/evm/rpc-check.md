# RPC 诊断（RPC Diagnostics）· EVM

> 在你当前的网络环境下逐个探测 RPC 端点：能不能连、是不是这条链、落后多少块、支持哪些只读能力。

## 什么时候用

- 某个工具一直转圈或报错，想确认是端点的问题还是别的原因。
- 手上有几个候选端点，想挑一个当前可用的。
- 需要 `debug_traceTransaction` 或历史状态，想先确认端点支不支持。

## 使用步骤

1. 选**期望网络**——用于比对端点实际返回的 `chainId`。
2. 把 **RPC 端点**贴进来，每行一个（最多 8 个）。
3. 点**开始探测**。端点会**逐个串行**探测：并发只会互相拖慢，还更容易触发对端限流。

## 输出说明

| 列 | 含义 |
| --- | --- |
| 状态 | 可用 / 浏览器连不上 / 被限流 / 需要授权 / 应答异常 |
| chainId | 端点实际返回的链 ID；与期望网络不符时高亮告警 |
| 区块高度 | `eth_blockNumber` 结果，可用于判断是否落后 |
| 响应时间 | 多次采样的中位数 |
| 只读能力 | `eth_call` 与历史状态（archive）的支持情况，三态：支持 / 不支持 / 未知 |

## 注意事项 & 常见坑

这几条决定了你该怎么读这份结果：

- **「连不上」不等于节点挂了。** 浏览器把 CORS、DNS 解析失败、网络不通、端点不存在收敛成同一个错误，JavaScript 拿不到区别。所以这里列出的是全部可能原因，而不是替你断言某一个。
- **响应时间不是端点质量排名。** 它只反映你此刻的网络与本次采样窗口，换个地区、换个时间结论可能完全相反，也不能拿来跨端点做"谁更快"的结论。
- **历史状态探测一次成功不证明完整 Archive。** 所以结果里会写明用的是哪个区块——只有对着那个区块，结论才有意义。想确认更早的历史，需要自己用更早的区块再试。
- **「未知」不等于「不支持」。** 探测被限流、样本无效等情况都会导致判不出来，这时报的是"未知"。把未知当成不支持会让你误伤可用的端点。
- **带 API Key 的地址会被标出来。** 这类地址不要写进分享链接或未脱敏的导出文件。
