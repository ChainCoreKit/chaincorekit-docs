# 地址预测与 Merkle（Address Prediction & Merkle）· EVM

> 部署前算出合约地址；为空投白名单生成 Merkle root 与 proof，叶子编码方案显式可选。全部本地计算。

## 什么时候用

- 部署前想知道合约会落在哪个地址（比如要先把资金打过去，或先写进别的合约）。
- 用 CREATE2 工厂做跨链同地址部署，需要先确认 salt 与 initCode 对不对。
- 做空投，需要一个 Merkle root 写进合约，以及每个地址的 proof。

## 合约地址预测

### CREATE

地址只由**部署者地址 + 该地址当时的 nonce** 决定，与合约内容无关。所以你能预测自己下一次部署的地址——但只要中间插进别的交易，nonce 就变了，地址也就变了。

### CREATE2

地址由**工厂地址 + salt + initCode 哈希**共同决定，与 nonce 无关。这正是跨链同地址部署的原理：三样完全一致，地址就一致。

> **initCode 不是运行时字节码。** 这是最常见的用错：initCode 是「构造函数字节码 + 编码后的构造参数」，运行时字节码是部署完成后链上存的那一段。传错了算出来的地址永远对不上。

> 地址算得出来，不代表那条链上一定部署得成功——工厂合约得存在、salt 不能已被用过。

## Salt 搜索（Salt Miner）

想让合约地址带上指定的前缀或后缀（比如 `0x0000…`），就在这一页填工厂地址与 initCode，给出想要的 hex 前后缀，浏览器本地逐个试 salt。

**salt 与靓号钱包完全不是一回事。** 靓号搜索找的是私钥，找到就等于拿到资产控制权；salt 只是一个公开的部署参数，谁都能拿着同样的工厂地址与 initCode 重算出同一个结果。搜出一个好看的 salt 不涉及任何秘密，因此这里的起点固定从 0 开始，也不需要安全随机源。

**难度：每多一位 hex 字符，期望次数乘以 16。**

| 前后缀合计位数 | 期望尝试次数 |
| --- | --- |
| 4 位 | 约 6.5 万 |
| 5 位 | 约 105 万 |
| 6 位 | 约 1677 万 |
| 8 位 | 约 43 亿 |

浏览器里 4–5 位是实用的，6 位要等一会儿，再多就该用 GPU 方案了。页面上会先把期望次数和当前速度显示出来，你可以据此判断值不值得等。

搜索期间可随时**停止**；离开这个页面会自动停下（否则后台会继续占 CPU），回来需要重开。

## Merkle 白名单

### 叶子编码方案必须显式选择

这是本页最重要的一条。业界有两套常见写法，**同一批数据算出的 root 完全不同**：

| 方案 | 叶子哈希 | 常见于 |
| --- | --- | --- |
| **OpenZeppelin StandardMerkleTree** | `keccak(keccak(abi.encode(值)))` —— **双重哈希** | OZ 的 `MerkleProof` 配套用法 |
| **merkletreejs（encodePacked）** | `keccak(abi.encodePacked(值))` —— **单次哈希** | 较早的教程与示例代码 |

多数在线 Merkle 工具**不告诉你它用的是哪一套**，于是你算出的 root 与合约里校验的对不上，而两边看起来都完全正常。所以这里强制你选，并把选择显示在旁边。

「对叶子排序」「配对时排序」两个开关同样会改变 root——它们必须和你合约里的实现一致。

### 导出

导出的 CSV **带上构造参数**（编码方案、列类型、两个排序开关、root），因为只有 root 和 proof 的话，别人拿到也复现不出同一棵树。

## 注意事项 & 常见坑

- **root 算错的后果是空投合约拒绝所有人**，而错误的 root 和正确的看起来一模一样。上线前请用少量地址在测试网实际验一次。
- **列类型要与合约里的 `abi.encode` 顺序一致**，多一列少一列都会得到另一个 root。
- 本工具只生成 root 与 proof，**不创建领取合约**——白名单资格验证与实际发放是两件事。
